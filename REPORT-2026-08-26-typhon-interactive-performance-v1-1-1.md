# Typhon Interactive Performance v1.1.1 — Scheduler-Accurate Interaction Closure

Date: 2026-08-26
Baseline: `8b9dd1b` (`perf: close remaining interactive hot paths`)
Repository: `/home/agony/GitHub/Typhon`

## Outcome

Interactive move and resize visuals are now scheduler-admitted. Raw input keeps
precise protocol delivery and replaces only the latest desired visual target.
The first pending target queues visual work; later replacements do not request
another primary scene cycle. Floating and tiled geometry are consumed only by
the final composited `Render`/`RenderAhead` path.

No real native KMS CPU/GPU benchmark was available in this environment, so this
report makes no host-performance claim.

## Revalidated root cause

Before this closure, `CompositorState::has_pending_frame_prepare_work()` treated
pending floating and tiled interaction geometry as generic prepare work. Native
cycle preparation runs before the frame scheduler chooses `Render`, `RenderAhead`,
or a wait decision, so `CompositorServer::prepare_frame()` could apply expensive
geometry on input-driven cycles. Active interaction handling also used one
boolean for both “target changed” and “request a full visual cycle”; hardware
cursor movement could therefore be misclassified as primary scene work.

## Architecture implemented

- Added `InteractionUpdateOutcome::{NoChange, ReplacedPending,
  QueuedNewVisualWork}` and `has_pending_interactive_visual_work()`.
- Narrowed generic `prepare_frame()` to explicit-sync, color, resize-configure,
  and client-flush responsibilities. It no longer applies floating or tiled
  interaction geometry.
- Added `flush_pending_interactive_visual_state_for_render_admission()` as the
  single visual-consumption authority. It applies tiled then floating state,
  records the admission, flushes the configure protocol generated by admitted
  XDG resize geometry, and flushes clients.
- Gated admission after scheduler, plane/direct, and atomic-lane decisions, and
  before scene/damage capture. Pending interaction work is composition-required
  and direct-scanout-ineligible for that frame. Published scene facts are then
  refreshed from the post-apply generation.
- Added `visual_work_deadline_due` to native runtime state. A queued scheduler
  deadline wakes presentation when due, while a pure input wake during a
  not-yet-due queued opportunity remains outside the scene domain.
- Kept terminal release/cancellation flushes explicit and exact.

Core files changed:

- `src/compositor/interaction.rs`, `src/compositor/mod.rs`;
- `src/compositor/state/frames.rs`, `src/compositor/state/window_interaction.rs`;
- `src/compositor/server.rs`;
- `src/native_output/input/routing.rs`;
- `src/native_output/runtime/cycle.rs`, `work_domains.rs`,
  `presentation_cycle.rs`, `presentation_direct.rs`;
- focused compositor/native test support and interaction tests.

## Behavior and protocol ordering

Floating move stores the latest pointer placement and applies it only at a
composited render admission. XDG position-only movement remains configure-free.
Floating XDG resize consumes the latest clamped geometry once per admission,
preserving duplicate suppression, bounded configure/ACK/captured-commit flow,
edge anchoring, and final `resizing=false` behavior. X11 behavior remains on
the existing admitted/terminal paths.

Tiled/Dwindle input stores the latest requested ratio. Topology-generation,
handle ownership, constraint clamping, and layout authority are unchanged; the
full tree solve and plan application occur only at admission.

Ready frame scene identity remains immutable. A newer interaction target stays
pending while a ready frame, O1 credit, worker queue, pageflip, or KMS lane owns
the current frame. The interaction admission cannot use the direct-scanout or
plane-only path, and `RenderAhead` uses the same composited authority while
preserving existing worker/O1 ownership.

## Deterministic operation counts

- Floating resize: 1,000 raw updates, 999 pending replacements, zero visual
  applications before admission, one admitted visual application, and one
  separately justified terminal exactness flush.
- Tiled/Dwindle resize: 1,000 raw updates, 999 pending replacements, zero
  pre-admission layout flushes/solves, and one latest-ratio layout application.
- Scheduling: one `QueuedNewVisualWork` edge per pending interval; replacement
  outcomes do not queue another edge. Hardware cursor replacement samples do
  not request primary redraw; software cursor movement retains its repaint
  contract.
- Generic `prepare_frame()`: repeated prepare calls leave pending interaction
  state retained and do not apply interaction geometry.
- Non-render admission counter: zero by construction; admission is reachable
  only from composited `Render`/`RenderAhead` decisions after the final guards.

## Review Pass 1 — correctness and ownership

The review found and fixed the configure-order issue caused by applying XDG
resize geometry after generic prepare: the admission API now flushes the
resulting sendable configure. It also updated synthetic helpers that genuinely
represent a frame admission. The final source review found no pre-scheduler
floating/tiled consumer, no ready-frame relabeling, no direct/plane bypass, and
no stale pre-apply scene capture on the interaction render path.

## Review Pass 2 — performance and regression challenge

The independent search found no raw-frequency tiled solve, repeated visual-work
queue, hardware-cursor primary redraw, fixed-refresh timer, hot-path diagnostic
allocation, or sticky queued-redraw promotion while a scheduler deadline is
future. The 1,000-sample tiled and floating tests exercise replacement at raw
frequency and admission at one visual opportunity, rather than batching all
samples behind a single generic prepare call.

## Remaining risks and hardware gates

Real-session qualification remains outstanding: measure native KMS CPU time,
GPU/render time, refresh cadence, dropped/deferred frames, and configure/ACK
latency with hardware cursor, software cursor, XDG resize, X11 interaction,
O1/render-ahead, KMS worker, direct-scanout transition, and Dwindle workloads.
The deterministic suite demonstrates the ownership and operation-count gates;
it does not substitute for that host measurement.
